# Polsia — Autonomous Business OS: Implementation Plan

**Scope decision:** This pass delivers **Phase 0 + Phase 1** (architecture foundation + multi-tenant foundation), ending at a clean, tested, documented milestone. The full roadmap for Phases 2–9 is defined below as the architectural target so Phase 0–1 code is shaped correctly, but only Phases 0–1 are implemented now.

**Stack (decided):** Python 3.12, FastAPI, SQLAlchemy 2 (async) + Alembic, PostgreSQL, Pydantic v2, pytest + pytest-asyncio, ruff + mypy, Docker Compose for dev.

## PHASE 0 — Architecture & Repository Rules

### 0.1 Repository scaffolding & governance docs
Deliverables:
- **`docs/ARCHITECTURE.md`** — single source of truth for architecture: layer diagram, the User→Org→Company→State→CEO→Orchestrator→Agents→Skills→Tools→Memory→Events loop, module boundaries, dependency rules (core layer must not import from API or adapters), naming conventions, and the business-agnosticism rules (no industry/domain enums, no hardcoded business metrics — all domain data is schema-flex / configuration).
- **`docs/ROADMAP.md`** — Phases 0–9 with entry/exit criteria per phase (content summarized in the roadmap section below).
- **`docs/DECISIONS/`** — lightweight ADRs (decision record per major choice: stack, tenancy model, ID strategy, event envelope).
- **`CONTRIBUTING.md`** — subagent orchestration policy codified for this repo: max 5 concurrent subagents, required subagent brief fields (objective, scope, files, constraints, expected output, validation), integration-only-by-lead rule.
- Project skeleton: `pyproject.toml` (deps, ruff, mypy strict, pytest config), `Makefile` (`make dev`, `test`, `lint`, `migrate`, `seed`), `.env.example`, `.gitignore`, `git init` + initial commit.

### 0.2 Layered architecture convention (enforced in code layout)
```
polsia/
├── core/            # domain entities, value objects, interfaces (ports) — zero I/O deps
│   ├── tenancy/     # User, Organization, Company entities + ports
│   ├── state/       # CompanyState aggregate (Phase 2 target)
│   └── shared/      # ids, errors, result types, pagination
├── adapters/        # implementations of core ports (DB repos, event bus, memory, tools)
│   ├── persistence/ # SQLAlchemy models, repositories, Alembic
│   ├── events/      # in-process event bus (Phase 1) → durable bus (Phase 2)
│   └── runtime/     # agent runtime port + mock (Phase 3)
├── services/        # application/use-case layer (orchestrates core + adapters)
├── api/             # FastAPI routers, schemas, auth, tenant context middleware
└── infra/           # settings, logging, db session, DI wiring
```
Rule: `core` imports nothing above it; `api`/`adapters` depend on `core` via interfaces; all wiring in `infra`. CI lint rule checks imports (ruff `TID`/custom check).

### 0.3 Cross-cutting foundations (shared with Phase 1)
- Typed ID system: strongly-typed IDs (`UserId`, `OrganizationId`, `CompanyId`) as `str` subclasses with prefix scheme (`usr_`, `org_`, `cmp_`), generated as ULIDs for sortability.
- Error taxonomy: `PolsiaError` hierarchy → domain errors → API problem-details responses (RFC 9457).
- Observability baseline: structlog JSON logging, request/trace IDs on every log line and response header, `/healthz` + `/readyz`.
- Settings via pydantic-settings, 12-factor.

## PHASE 1 — Multi-tenant Foundation (User / Organization / Company / DB / API)

### 1.1 Database & tenancy model (Database Engineer)
- PostgreSQL schema, Alembic migrations:
  - `users` (id, email unique, hashed_password, display_name, status, timestamps)
  - `organizations` (id, name, slug unique, owner_user_id, status, timestamps)
  - `org_memberships` (org_id, user_id, role ∈ {owner, admin, member}, unique(org_id, user_id)) — many-to-many, roles extensible later
  - `companies` (id, org_id FK, name, slug, **identity jsonb**, **mission text**, **strategy jsonb**, **configuration jsonb**, status ∈ {draft, active, paused, archived}, timestamps) — identity/mission/strategy are business-agnostic flexible fields; the OS imposes no schema on what the company *does*.
- Tenancy enforcement: every company query is scoped by org; tenant context resolved from authenticated user + org header/path; repository layer takes tenant scope as a mandatory parameter (no global implicit tenant).
- Async SQLAlchemy 2.0 with `asyncpg`; UUID(ULID) primary keys; `created_at`/`updated_at` on all tables.

### 1.2 Domain core (Backend Engineer)
- Entities + invariants in `core/tenancy/`: User, Organization, Company, OrgMembership with factory methods enforcing invariants (slug format, status transitions as explicit state machine: draft→active→paused→archived with forbidden transitions raising domain errors).
- Repository ports in `core`, SQLAlchemy implementations in `adapters/persistence` (duck-typed, swappable for tests with in-memory fakes).

### 1.3 API layer (Backend Engineer)
- FastAPI app with routers:
  - `POST /auth/register`, `POST /auth/login` (JWT access + refresh), `GET /auth/me`
  - `POST /organizations`, `GET /organizations` (mine), `GET/PATCH /organizations/{id}`, membership listing + invite-add member endpoint
  - `POST /organizations/{org_id}/companies`, `GET/PATCH /organizations/{org_id}/companies/{id}` (identity/mission/strategy updates), `POST .../companies/{id}/status` (state-machine transition), list companies
- Auth: password hashing (argon2/bcrypt via passlib), JWT bearer, org-membership authorization dependency (403 unless member; role checks for mutations).
- OpenAPI docs auto-generated; request/response schemas in Pydantic v2, domain entities never leak directly.

### 1.4 Events (thin slice, proves the event abstraction early)
- `EventEnvelope` port + in-process pub/sub adapter in Phase 1; emit `user.registered`, `organization.created`, `company.created`, `company.status_changed` on the existing mutations. No subscribers yet beyond a log subscriber — full bus + subscriptions land in Phase 2.

### 1.5 Testing (QA Engineer)
- Unit tests for domain invariants & state machine (no DB).
- Repository integration tests against Postgres via Docker Compose (testcontainers-style or compose test profile).
- API tests: auth flows, tenancy isolation (user B cannot read/modify org A's companies — dedicated test suite), role authorization, status-transition rejection cases.
- Coverage gate ≥ 85% on `core/` and `services/`.

### 1.6 DevOps & docs (DevOps + Docs)
- `docker-compose.yml`: postgres + api (dev with reload); `Dockerfile` (multi-stage, non-root).
- CI (GitHub Actions): lint (ruff), typecheck (mypy), tests (postgres service container), on every push/PR.
- `README.md`: quickstart (clone → `docker compose up` → register user → create org → create company via curl examples); `docs/API.md` generated endpoint reference; seed script creating a demo user/org/company for local dev.
